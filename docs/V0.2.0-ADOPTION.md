# v0.2.0 adoption checklist (web, iOS, Android)

`@curio/contracts` v0.2.0 makes the most-to-pay, the fee position and the tax rate nullable, and a
null always carries a reason. It is **source-breaking on every platform** and is adopted in lockstep
(Ben, `LANE-REPORTS/owner.DESIGN-REVIEW-2026-10.md`, "Rulings, round 2", item 1). Round 2 of the
same release (2026-10-08) also attaches the priced breakdown to real responses, models one closed
listing-refusal vocabulary and game availability, puts a non-null opaque SKU on every copy, and adds
`UNMATCHED` / `HELD` statuses. The full schema change and the invariants are in `CHANGELOG.md`
v0.2.0; this file is the work list. **The round-2 sections start at "Round 2: what else breaks".**

## The lockstep rule (read this first)

**Web, iOS and, if it ships, Android all adopt v0.2.0 BEFORE the server sends any `null` for a
most-to-pay, a fee, a tax rate or a seller type.** Until all of them have shipped, the server keeps
sending today's shape (numbers: `maxBuyGbp`, `feeGbp`, `taxRate` 0.2, `sellerType` "private" for a
profile row) behind a server-side switch it can flip back. A v0.1.45 client fails the WHOLE
`Decision` / `CardValueResponse` / `ProfileResponse` on the first null, not the field. The switch is
global (there is no per-request flag).

**What "adopted" means (Ben, 2026-10-09; settles the draft's open item 1).** The server flag
`ECONOMICS_V2_WIRED` stays OFF until ALL of these are true:
1. **Web** is deployed on v0.2.0 (not merely merged);
2. the **iOS** build and, if it ships, the **Android** build on v0.2.0 are MERGED;
3. a **minimum-version check** is in place before any outside tester receives a build, so a tester
   on a v0.1.x build is told to update instead of losing the whole `Decision` / `CardValueResponse`
   / `ProfileResponse` to the first null.
Until then the server keeps sending today's shape (numbers; `taxRate` 0.2; `sellerType` "private"
for a profile row). The flag is a server-side switch that can be flipped back, not a deploy.

| Who | Must adopt before the switch | What "adopted" means |
|---|---|---|
| **Web** (pokemon-tool) | bump the pin; build every response through the v0.2.0 schemas (they now REJECT an inconsistent response); add the breakdown, `sku`, `status`, `heldAt`; emit the `failure` envelope for the new refusals; route the new refusals through `card_not_listable` | the server compiles and parses its own responses; nothing null is sent yet |
| **iOS** | bump `exactVersion`; render `unknownReason` / `feeNotSetReason` / `maxBuyUnavailableReason` and a nil tax rate instead of a figure; render the breakdown lines instead of computing; stop sending `sku`; handle the six new `EbayPublishError` cases and `.unrecognised` everywhere | a build on v0.2.0 merged (and a minimum-version check before outside testers) |
| **Android** (if it ships) | the same decode/render changes for the shapes it consumes (Quick Scan: `Decision`, `breakdown`) | a build on v0.2.0 merged |

Not nulls, so NOT gated by the switch: the new required keys (`breakdown`, `sku`, `status`,
`heldAt`, `unknownReason`, `estimate`, `askingPriceOnly`) and the new endpoints (`GET /api/games`, the
listing preview). An older client ignores unknown keys (`ignoreUnknownKeys`), so web can start
sending them as soon as it has bumped. The first write of an `UNMATCHED` or `HELD` status is the one
other gated item: do not let a server path create one until iOS and Android render them (both come
from new UI, `A8b` "Keep it without a match" and `C19` Hold).

## The sequence, and what the server does at each step

1. Contracts merged; Ben tags `v0.2.0`.
2. **Web bumps and compiles. The server keeps sending numbers.** Every nullable field is non-null,
   `maxBuyUnavailableReason: null`, `feeNotSetReason: null`. Installed clients ignore the two new
   keys, so this step is invisible to them.
3. **iOS and Android bump, adopt and ship.** Nothing they receive changes yet.
4. **The server sends its first null only after all three have adopted.** A server-side switch.

### The switch

The ruling says "adopted in lockstep by web, iOS and Android before the server sends a null". Two
facts make "adopted" need a definition:

- A v0.1.45 client decodes `maxBuyGbp` as a non-optional `Double`. A JSON `null` fails the **whole
  `Decision`**, not the field. iOS's `decideFull` then returns `nil`
  (`ios/CurioCapture/Services/SupabaseService.swift:1312-1319`) and the lookup shows "No
  recommendation available" (`ios/CurioCapture/CurioCaptureApp.swift:1179`). Android's behaviour on a
  decode failure was not traced.
- Per-request gating is not available: Option A's `acceptsMaxBuyVerdict` flag was dropped, and the
  server does not know a client's build. So the switch is **global**, and a shipped adopting build is
  not the same as every installed build having updated.

**Decision for Ben before step 4:** what "adopted" means for iOS and Android. Options: (a) a minimum
share of installed builds on the adopting version, measured from the existing client-version signal,
if there is one; (b) a forced-upgrade floor in the app; (c) accept that older builds lose the
decision until they update. #224 §7 recommended waiting until the old-build share is "near zero". Not
decided here. Step 4 should be a flag the server can flip back, not a deploy.

## What is deliberately not in this release

- `acceptsMaxBuyVerdict` and a `Decision.maxBuy` object (#224 Option A): dropped by the ruling.
- `postage_rules` / Dispatch fields on the profile (#229): unsettled, and additive.
- A BulkRecord or lot wire type: no route defines one yet (#235, #233 are plans). When one exists:
  no `sku` on the record (only on its lot listing), no figure multiplied by a count, and a lot's
  cost share and value use the LOW END of the asking range, the same basis as lot appraisal.
- An hourly-rate field on the profile (H11d). The breakdown carries a `packing_time` line only when a
  rate exists, but where the rate (and the seller's own packing minutes) is stored and edited is not
  in the contract (open item 8). There is NO listing-time anywhere (Ben, 2026-10-09).
- `receive_changed` (409 on publish when the recomputed receipt differs, #220 question 2): undecided.
- A change of meaning for `DecideRequest.targetMarginPct` (share of buy price to share of sale price,
  #224 Decision 2). Not in the round-2 ruling; the field and its doc are untouched.
- (Round 2 reverses the draft here: selling-side tax IS "only when set". `taxRate` is nullable in
  `StoredPricingSettings` and `EffectivePricingSettings`; see round 2.)
- A way to clear a chosen buying margin back to "Not set": #224 defines none.

`ListingPreviewRequest/Response` (+ item, totals, group), `PostageMode`.

**Name warning (iOS).** `PhysicalCardStatus` cases for all-caps wire values follow the generator's
existing convention (the same one that gives `Condition.nM`): `.rEADYTOLIST`, `.nEEDSIDREVIEW`,
`.uNMATCHED`, `.hELD`. Ugly and stable. A nicer mapping is a generator change that would also rename
`Condition`'s cases; not done here (open item 9). Kotlin names are the plain wire values.

**What the generated types cannot enforce** (server-side guards, tested here, invisible to Swift and
Kotlin): null amount iff reason; the breakdown agrees with its decision; flat figures agree with the
breakdown; a preview's totals are the sum of its rows to the penny; sign (value positive, deductions
negative); `max_buy` a whole pound; `reason` present iff `card_not_listable`; `heldAt` present when
HELD. A client must not rely on them to reject bad data; it renders what it is given.

### The rulings, as the contract holds them

- **Rounding.** Each breakdown line is rounded to the penny; the total is the SUM OF THE ROUNDED LINES
  (selling: exactly; buying: that sum rounded down to the pound, never negative). One unknown included
  line makes the total null. Server-side guard + golden vector `total_is_not_the_sum_of_the_rounded_lines`
  (TS refuses it; Swift and Kotlin decode it, which is the point: no client re-adds).
- **You receive can be negative.** The true negative is sent (never clamped), with `note: "pays_to_sell"`
  on the `you_receive` line (renamed from the draft's `below_cost`, round 4); the client label is the
  copy key "You'd pay to sell this". `sale_price` and
  `max_buy` are never negative.
- **Packing time.** The line (negative, `minutes`, taken off) exists only when an hourly rate is set.
  Minutes are the seller's own setting or, if unset, the RULED DEFAULT: a flat 4 minutes a parcel and 2
  for each extra card, no letter/parcel split (`defaultPackingMinutes(cards)` = 4, 6, 8, ...). The
  line is `estimate: true` exactly when the default was used. (Listing time was removed in round 4.)
- **Postage precedence.** The eBay postage policy for PUBLISHED listings, Dispatch rules for
  ESTIMATES. The postage line says which, in a closed way: `postageBasis` = `ebay_policy` (then
  `source` is `ebay_policy` and `service` null: the policy has no Dispatch service) or
  `dispatch_rules`. Optional, so an older server still validates.
- **Value totals.** (Superseded in round 4: see below.) HELD copies count in the total with the held
  part apart; Not identified adds nothing.
- **Graded slabs.** An unverified slab is never listed as graded. `GradedCreateResponse.certVerified`
  is set only by the server (a PSA lookup whose grade agrees); the request carries no flag and no
  `sku`. Listing one is `card_not_listable` / `slab_unverified`.

### Request fields `postageFor` and `cardsInParcel` (added after round 3; pokemon-tool #255)

Both optional, additive and forward-compatible, so no client has to send either.
- `postageFor` (`PostageFor`: `estimate` | `published`), on `PricingBreakdownRequest` and, once for the
  whole batch, on `ListingPreviewRequest`. `estimate` (the default) prices postage on the seller's
  Dispatch rules; `published` on the eBay postage policy the listing uses. It is the request-side twin
  of the response's `postageBasis` (`dispatch_rules` / `ebay_policy`); the postage line reports what
  was actually used (with no usable policy, `published` answers as an estimate). Swift `.unrecognised`
  / Kotlin `Unknown` on a server that adds a value; a client never sends one it invented.
- `cardsInParcel` (integer 1 to 500, default 1), on `PricingBreakdownRequest` and per copy on
  `ListingPreviewItemRequest`: the cards in that parcel, which drives the packing-time default of
  4 minutes + 2 per extra card (`defaultPackingMinutes`). It is seller intent, not a figure the world
  sets (ADR 0028).
Swift/Kotlin: new optional parameters on the two request types (and the new `PostageFor` enum); a
memberwise-init caller that does not pass them is unaffected on Kotlin (defaults) and needs `nil` on Swift.

### The rulings, as the contract holds them

- **A figure from asking prices is a ceiling, not a null (rule 10).** The shape is a boolean
  `askingPriceOnly` on the figure (on `Decision` and on `PricedTotals`), not a new enum or a nested
  object, because it is the least breaking way to say it: one new bool beside a figure that already
  exists, the figure's type does not change, and a client that ignores the flag still shows the
  number (the safe direction). Guards: only with a shown figure; the decision and breakdown agree.
- **Listing time is gone everywhere.** No field, line, setting, calculation or vector. Packing time
  stays: 4 minutes a parcel + 2 per extra card in the same parcel, `estimate: true` when the default
  is used, taken off only when an hourly rate is set. `included` was only ever there to separate
  listing time and is removed with it (re-add it if a beside line ever returns).
- **Negative receive.** Kept as the true negative. The note code is renamed from `below_cost` to
  `pays_to_sell`: "below cost" compares to what the seller paid, which the contract never has, and
  the ruled wording ("You'd pay to sell this") is about fees and postage exceeding the price. The
  words are @curio/copy's, never the contract's.
- **Value totals (supersedes the round-3 "held out of totals" note).** HELD copies COUNT in
  `estValue`; the held part is returned apart as `heldValue`; Not identified adds nothing (no
  price); Mine stays apart in `collectionValue`; set-aside, sold and archived are in no value.
- **Inventory list vocabulary.** `InventoryStatusKey`: `ready`, `listed`, `held`, `needs_you`,
  `identifying`, `not_identified`, `mine`, `set_aside`, `sold`, `archived`. In-flight scans read
  "Identifying", not Needs you; "Archived" is a status filter value, off by default; Not identified
  is not pinned under Needs you; select-all is capped at 200 (`INVENTORY_SELECT_ALL_CAP`). Only the
  vocabulary is here; the row and summary shapes are the follow-up list contract (#258/#261).
- **Stop holding.** `POST /api/inventory/stop-holding {ids}` (`StopHoldingRequest`): a HELD copy goes
  back to READY_TO_LIST with no listing; per-copy `InventoryChangeResponse` like Mine / Put back;
  `unchanged` for a copy that is not held.
