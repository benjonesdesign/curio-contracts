# v0.2.0 adoption checklist (web, iOS, Android)

`@curio/contracts` v0.2.0 makes the most-to-pay, the fee position and the tax rate nullable, and a
null always carries a reason. It is **source-breaking on every platform** and is adopted in lockstep
(Ben, `LANE-REPORTS/owner.DESIGN-REVIEW-2026-10.md`, "Rulings, round 2", item 1). Round 2 of the
same release (2026-10-08) also attaches the priced breakdown to real responses, models one closed
listing-refusal vocabulary and game availability, puts a non-null opaque SKU on every copy, and adds
`UNMATCHED` / `HELD` statuses. The full schema change and the invariants are in `CHANGELOG.md`
v0.2.0; this file is the work list. **The round-2 sections start at "Round 2: what else breaks".**

## The lockstep rule (read this first)

**Web, iOS and, if it ships, Android all adopt v0.2.0 BEFORE the server sends any `null` for a
most-to-pay, a fee, a tax rate or a seller type.** Until all of them have shipped, the server keeps
sending today's shape (numbers: `maxBuyGbp`, `feeGbp`, `taxRate` 0.2, `sellerType` "private" for a
profile row) behind a server-side switch it can flip back. A v0.1.45 client fails the WHOLE
`Decision` / `CardValueResponse` / `ProfileResponse` on the first null, not the field. The switch is
global (there is no per-request flag), so "adopted" has to mean an installed share, not a merged PR
(open item 1 below).

| Who | Must adopt before the switch | What "adopted" means |
|---|---|---|
| **Web** (pokemon-tool) | bump the pin; build every response through the v0.2.0 schemas (they now REJECT an inconsistent response); add the breakdown, `sku`, `status`, `heldAt`; emit the `failure` envelope for the new refusals; route the new refusals through `card_not_listable` | the server compiles and parses its own responses; nothing null is sent yet |
| **iOS** | bump `exactVersion`; render `unknownReason` / `feeNotSetReason` / `maxBuyUnavailableReason` and a nil tax rate instead of a figure; render the breakdown lines instead of computing; stop sending `sku`; handle the six new `EbayPublishError` cases and `.unrecognised` everywhere | a shipped build, and (item 1) an agreed share of installed builds on it |
| **Android** (if it ships) | the same decode/render changes for the shapes it consumes (Quick Scan: `Decision`, `breakdown`) | a shipped build |

Not nulls, so NOT gated by the switch: the new required keys (`breakdown`, `sku`, `status`,
`heldAt`, `unknownReason`, `estimate`, `included`) and the new endpoints (`GET /api/games`, the
listing preview). An older client ignores unknown keys (`ignoreUnknownKeys`), so web can start
sending them as soon as it has bumped. The first write of an `UNMATCHED` or `HELD` status is the one
other gated item: do not let a server path create one until iOS and Android render them (both come
from new UI, `A8b` "Keep it without a match" and `C19` Hold).

`ci-workflow-dispatch`; `origin/main` has the same pin), the iOS working copy `ios/` at `c0ceba1`

## The sequence, and what the server does at each step

1. Contracts merged; Ben tags `v0.2.0`.
2. **Web bumps and compiles. The server keeps sending numbers.** Every nullable field is non-null,
   `maxBuyUnavailableReason: null`, `feeNotSetReason: null`. Installed clients ignore the two new
   keys, so this step is invisible to them.
3. **iOS and Android bump, adopt and ship.** Nothing they receive changes yet.
4. **The server sends its first null only after all three have adopted.** A server-side switch.

### The switch

The ruling says "adopted in lockstep by web, iOS and Android before the server sends a null". Two
facts make "adopted" need a definition:

- A v0.1.45 client decodes `maxBuyGbp` as a non-optional `Double`. A JSON `null` fails the **whole
  `Decision`**, not the field. iOS's `decideFull` then returns `nil`
  (`ios/CurioCapture/Services/SupabaseService.swift:1312-1319`) and the lookup shows "No
  recommendation available" (`ios/CurioCapture/CurioCaptureApp.swift:1179`). Android's behaviour on a
  decode failure was not traced.
- Per-request gating is not available: Option A's `acceptsMaxBuyVerdict` flag was dropped, and the
  server does not know a client's build. So the switch is **global**, and a shipped adopting build is
  not the same as every installed build having updated.

**Decision for Ben before step 4:** what "adopted" means for iOS and Android. Options: (a) a minimum
share of installed builds on the adopting version, measured from the existing client-version signal,
if there is one; (b) a forced-upgrade floor in the app; (c) accept that older builds lose the
decision until they update. #224 §7 recommended waiting until the old-build share is "near zero". Not
decided here. Step 4 should be a flag the server can flip back, not a deploy.

## What is deliberately not in this release

- `postage_rules` / Dispatch fields on the profile (#229): unsettled, and additive.
- A BulkRecord or lot wire type: no route defines one yet (#235, #233 are plans). When one exists:

  `listing_time` lines only when a rate exists, but where the rate is stored and edited is not in
  the contract (open item 8).
- `receive_changed` (409 on publish when the recomputed receipt differs, #220 question 2): undecided.
- A change of meaning for `DecideRequest.targetMarginPct` (share of buy price to share of sale price,
  #224 Decision 2). Not in the round-2 ruling; the field and its doc are untouched.
- (Round 2 reverses the draft here: selling-side tax IS "only when set". `taxRate` is nullable in
  `StoredPricingSettings` and `EffectivePricingSettings`; see round 2.)
- A way to clear a chosen buying margin back to "Not set": #224 defines none.

New types (additive): `PhysicalCard`, `PhysicalCardStatus`, `ListingRefusal` (+ `Code`, `Reason`),
`GamesResponse`, `GameInfo`, `GameAvailability`, `GameRefusal` (+ `Code`), `UnavailableGame`,
`ListingPreviewRequest/Response` (+ item, totals, group), `PostageMode`.

**Name warning (iOS).** `PhysicalCardStatus` cases for all-caps wire values follow the generator's
existing convention (the same one that gives `Condition.nM`): `.rEADYTOLIST`, `.nEEDSIDREVIEW`,
`.uNMATCHED`, `.hELD`. Ugly and stable. A nicer mapping is a generator change that would also rename
`Condition`'s cases; not done here (open item 9). Kotlin names are the plain wire values.

**What the generated types cannot enforce** (server-side guards, tested here, invisible to Swift and
Kotlin): null amount iff reason; the breakdown agrees with its decision; flat figures agree with the
breakdown; a preview's totals are the sum of its rows to the penny; sign (value positive, deductions
negative); `max_buy` a whole pound; `reason` present iff `card_not_listable`; `heldAt` present when
HELD. A client must not rely on them to reject bad data; it renders what it is given.

## Decisions for Ben (round 2) and what was decided here

Decided here (so the contract is complete; change any with a rename plus a lockstep release):

- The refusal family models `card_not_listable` + reason, not #243's flat codes (mapping above).
- `held` is not a refusal reason (domain model: a held copy can be listed on purpose).
- `GET /api/games` follows #228/#246 (`game`, `displayName`, `availability`), not the brief's `id`,
  `name`, `enabled`: a boolean cannot say "coming".
- `max_buy` is whole pounds, rounded down by the server; value lines positive, deductions negative.
- `EbayPublishRequest.sku` is removed, not made optional, because no request may carry a SKU.
- Listing time lives in `beside`, never `lines`, as a positive magnitude with `included: false`
  (per the owner and pokemon-tool #244); packing time is a negative line with `minutes`.

Open (the question for Ben):

1. **What "adopted" means for the switch** (round 1, above).
2. **One refusal vocabulary, or keep #243's flat codes?** Recommended: `card_not_listable` + reason.
3. **One HTTP status per code?** `condition_not_confirmed` is 422 in #243 and the spec's C16b, and
   409 here (all `card_not_listable` is 409). Alternative: 422 for the validation-like reasons
   (`condition_not_confirmed`, `no_price`, `no_sku`) and 409 for the state ones.
4. **Is `Decision.maxBuyGbp` pence or whole pounds?** The contract enforces only
   `floor(decision.maxBuyGbp) === breakdown total`, which holds both ways. Recommended: the same
   whole-pound figure everywhere, so no client shows £84.77 on one row and £84 on another.
5. **Which path serves the listing preview?** #220 says `POST /api/pricing/breakdown/batch`; #222
   says `POST /api/listing-batches/preview`. The schema is path-neutral; pick one.
6. **What the floor tests** (asking price, money received, or profit): `ListingPreviewResponse` reports
   the floor and the outcome and does not decide the basis (#220 §6; `decideRoute` tests profit today).
7. **`minAcceptGbp` nullable** (round 1 item 2) and, new: when no tax rate is set, should
   `Decision.economics.taxProvisionGbp` be `0` or null? Today it is null only together with the fee.
   A `0` there reads as a chosen "no provision"; a null needs its own reason code. Left as drafted
   (unchanged), because the owner correction names only the profile fields and the breakdown line
   (`tax_set_aside` is simply absent without a rate).
8. **Where the hourly rate lives** (H11d): `packing_time` / `listing_time` appear only with one, but
   no profile field is in the contract, and the packing-minutes default is Ben's (H "For Ben").
9. **Nicer Swift case names for all-caps wire values** (`.readyToList` instead of `.rEADYTOLIST`):
   a generator change that also renames `Condition`'s cases.
10. **One tax rate or two?** `Profile.buyingTaxRate` (new, #224) and `pricingSettings.taxRate` (now
    also null = not set) both exist; if "tax applies only when set, buying and selling" is one
    setting, they should merge.
11. **Lot / BulkRecord wire type**: none exists; add a stub now or wait for the route (#235)?
